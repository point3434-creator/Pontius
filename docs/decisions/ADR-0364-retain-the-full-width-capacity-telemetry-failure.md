## ABI diagnosis

The v1 boundary calls `GetCurrentProcess` and `GetProcessMemoryInfo` through
`ctypes.windll` without declaring `argtypes` or `restype`. ctypes therefore
uses its legacy default integer ABI, which is not a valid authority for a
64-bit Windows `HANDLE`. An out-of-owner diagnostic using the same 80-byte
`PROCESS_MEMORY_COUNTERS_EX` structure established:

- explicitly typed `psapi.GetProcessMemoryInfo` returns true with last error
  zero;
- explicitly typed `kernel32.K32GetProcessMemoryInfo` independently returns
  true with last error zero; and
- PowerShell exposes finite process working-set, peak-working-set, and private
  byte values at the same boundary.

Those process-byte values vary across diagnostic processes and are not target
evidence or successor gates. The stable conclusion is the ABI defect: explicit
function signatures make both official entry points succeed, while the sealed
untyped call produced the retained failure. Confidence is high that the
missing 64-bit signature is the binding defect; v2 must still carry a live
cross-source sanity control rather than trust this diagnosis alone.
