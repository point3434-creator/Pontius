## Decision

It may not seal against the false hashes. Supersede exactly those three
metadata values with the correction config, preserve ADR-0433 and every parent
byte, strengthen the hash controls, and rerun the unchanged source-only gate.

The defect is identical in mechanism to ADR-0424. The hash receipt replaced
the four literal source bytes backslash, `r`, backslash, `n` with backslash,
`n`. Each affected Python parent contains that literal token inside its own
canonical-LF helper. The receipt therefore hashed altered source text rather
than source bytes with CRLF line endings normalized. Files without the token
appeared to rebind and hid the error.

The correct canonical-LF operation reads bytes and replaces only byte `13`
immediately followed by byte `10` with one byte `10`. All three parents use LF
ordinary lines and are unchanged from their historical source-seal commits.

## Structural repair for the recurring family

ADR-0424 already named R183, but its lesson was copied as prose rather than
made compulsory at this new config boundary. ADR-0434 therefore requires all
of the following for this seal and future source-hash receipts:

1. Hash both configs as immutable inputs.
2. Run the production canonical-LF helper in language over the actual parent
   bytes.
3. Independently normalize with a byte loop that neither calls nor copies the
   production replacement expression.
4. Require exact agreement over every bound parent before a config can seal.
5. Run the forbidden literal-token rewrite only as a mutation and prove that
   it reproduces, but cannot authorize, the three historical false values.
6. Never edit a parent to make false metadata true, and never accept a
   shell-quoted one-off digest as authority.

The recurring defect remains in the risk register until this mechanical
conformance suite passes. A passing source seal retires the observed instance,
not every untested hash-producing workflow in the repository.
